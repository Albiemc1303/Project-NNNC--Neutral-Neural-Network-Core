DOCUMENT CONTROL AND STATUS
Purpose
This document establishes the amended formal transition semantics governing the Phase 0 NNNC boundary architecture.
Revision v1.3.1 addresses blocking findings identified during independent technical review of Document 2 v1.3. It clarifies authoritative state management, execution fencing, lifecycle transitions, recovery-cycle semantics, activation protocols, clock domains, and verification requirements.
The amendment preserves the established NNNC–NES architectural distinction and the protected existential foundation.
It does not introduce new general cognitive capabilities or replace the wider NNNC architecture.
Normative Status
Revision v1.3.1 forms part of the conditionally accepted Phase 0 architectural baseline.
The acceptance of this architectural baseline does not constitute certification of the complete executable implementation.
The following distinctions remain mandatory:
• Architectural acceptance: The specification is sufficiently defined to serve as a controlled foundation for subsequent work.
• Reference-model conformance: A formal transition model satisfies specified properties within declared assumptions and verification bounds.
• Implementation conformance: Executable software implements the required transitions and passes applicable tests.
• Deployment conformance: The implementation additionally satisfies the durability, security, isolation, concurrency, and fault-tolerance requirements of its operational environment.
These classifications shall not be treated as interchangeable.
Amendment Precedence
Where this amendment conflicts with Document 2 v1.3, the provisions of v1.3.1 take precedence.
Unchanged requirements of Document 2 v1.3 remain applicable.
The inherited requirement, invariant, and test registers remain subject to reconciliation against their authoritative sources.
Document integrity qualification: This document is the complete supplied v1.3.1 amendment, not a verbatim reproduction of the underlying Document 2 v1.3. It must be read together with the unamended provisions of that specification.

1. REVISED FORMAL STATE
1.1 Authoritative State Separation
The former global-state interpretation is replaced by:
[ \boxed{\Omega_k=(\Sigma_k,\Pi_k,\mathcal J_k)} ]
Where:
• (\Sigma_k) is the governed NNNC domain state.
• (\Pi_k) is trusted non-rollback authority and accounting state.
• (\mathcal J_k) is the append-only audit history.
The original 17-part domain-state organization remains:
[ \Sigma_k=(R,D,F,O,K,A,L,B,H,J,M,T,X,Y,Z,G,W)_k ]
However, fields containing authority-sensitive information are now views or references to canonical records in (\Pi).
For example, the authorization view in (A) must not override the authoritative policy in (\Pi).
1.2 Protected Authority State
Define:
[ \Pi_k=(P_k,V_k,E_k,S_k,Q_k,I_k,C_k) ]

Field
Meaning

(P)
Current governance policy and version

(V)
Revocation history and effective revocation state

(E)
Fencing-generation high-water marks

(S)
Current session-authority registry

(Q)
Canonical budget and reservation ledger

(I)
Event-idempotency and replay-protection records

(C)
Clock-domain and trusted-control metadata


Ordinary checkpoint restoration SHALL NOT overwrite these records.
1.3 Audit History
For each event whose outcome is auditable:
[ \mathcal J_{k+1}=\mathcal J_k\mathbin{|}record_k ]
Accepted transitions, rejected protected operations, administrative interventions, and restoration attempts SHALL be distinguishable in audit records.
A rejected command may append an audit record without changing protected domain state.
1.4 Event-Processing Order
Let (j) count processed event decisions and (k) count committed domain transitions.
Thus:
[ j\in\mathbb N,\qquad k\in\mathbb N ]
A rejection increments the event-decision sequence but need not increment the committed domain-state version.
This avoids treating a rejected command as a fictitious successful domain transition.

2. NON-ROLLBACK AUTHORITY AND SESSION FENCING
2.1 Fencing Generation
For each instance (n), define:
[ E(n)\in\mathbb N ]
as the authoritative generation high-water mark.
Every issuance of new execution authority SHALL satisfy:
[ E_{\mathrm{new}}(n)>E_{\mathrm{previous}}(n) ]
Ordinary restoration SHALL NOT decrease (E(n)).
2.2 Current Authority
Define:
[ S(n)=(sessionId,generation,holder,status) ]
Where status is one of:
[ {ACTIVE,FENCED,REVOKED} ]
Only an ACTIVE authority record permits ordinary protected writes.
2.3 Protected Write Authorization
For a protected write event (e):
[ \begin{aligned} WriteAllowed(e,n)\iff{}& Authorized(e)\ &\land Lifecycle(n)=ACTIVE\ &\land e.sessionId=S(n).sessionId\ &\land e.generation=S(n).generation\ &\land S(n).status=ACTIVE\ &\land ResourceFenceAccepts(e) \end{aligned} ]
Administrative maintenance and shutdown operations use separately authorized control-plane transitions rather than ordinary cognitive write authority.
2.4 Resource-Side Fencing
A protected resource SHALL reject writes carrying a generation older than its trusted accepted-authority generation.
For the Build 2 reference model, resource-side fencing is simulated by an independently modeled protected-store guard.
This does not establish protection against rollback of the trusted store itself.
2.5 Checkpoint Restoration
A checkpoint's sourceSession and sourceEpoch are historical metadata.
They SHALL NOT directly become current authority.
Restoration performs:
1. Validate checkpoint integrity.
2. Validate current governance policy.
3. Validate current revocations.
4. Validate available budgets.
5. Fence prior execution authority.
6. Allocate fresh execution authority.
7. Restore permitted domain-state partitions.
8. Reconcile pending transactions and external effects.
9. Commit the new lifecycle state.
If the transaction fails before authority issuance, it must leave current authority unchanged or safely fenced.
If it fails after authority issuance, the issued generation remains consumed and cannot be reused.
2.6 Independent Branching
A restored independent branch SHALL receive:
• A fresh NNNC instance identifier.
• Fresh constituent component identifiers.
• A fresh execution-session identifier.
• A separately allocated fencing generation.
• A lineage reference to its source.
A branch SHALL NOT reuse the original instance's active membership identifiers.
2.7 Anti-Resurrection Invariant
For any event (e) created under authority (s_{\mathrm{old}}):
[ Fence(s_{\mathrm{old}}) \Rightarrow \Box\neg WriteAllowed(e) ]
This property holds under the assumption that trusted authority and resource-side fencing records are not rolled back.
It is a required safety property, not an established proof.

3. CLOCK-DOMAIN SEMANTICS
3.1 Trusted Clock Representation
Build 2 uses integer monotonic ticks:
[ Clock=(domainId,ticks) ]
Where:
[ ticks\in\mathbb N ]
A deadline is represented as:
[ Deadline=(domainId,dueTick) ]
3.2 Comparability
Two clock values may be directly compared only when their domain identifiers match.
A deadline from a previous clock domain SHALL NOT be evaluated against the current domain without an authorized rebase.
3.3 Restart Behavior
On a clock-domain restart:
1. The trusted control plane establishes a new clock-domain identifier.
2. Old timer deliveries are invalidated.
3. Open activation requests are cancelled or reconstructed under a new authorized request generation.
4. New deadlines are derived from declared remaining-duration or restart policy.
5. Reconstructed requests retain their incident-level consumed-budget history.
A restart SHALL NOT replenish wake-up allowances.
3.4 Suspension Behavior
During SUSPENDED, no ordinary heartbeat wake-up or recovery-attempt admission is permitted.
Time may continue advancing in the underlying substrate, but suspended-instance activation deadlines are invalidated or explicitly paused according to the suspension transaction.
On resumption, new deadlines must be established in the active clock domain.
3.5 Timer Delivery
A trusted timer event contains:
[ TimerEvent=(id,domainId,dueTick,observedTick) ]
A stale-domain timer event is rejected.
Timer expiry is evaluated at the committed transition point.
3.6 Timer Failure
The timer service is an explicit dependency and fault domain.
A lost timer event does not create an imaginary transition.
The implementation SHOULD support bounded periodic re-evaluation while the timer service is operational.
No deadline-response guarantee is claimed if all relevant timer-delivery mechanisms fail.

4. RECOVERY-MANAGER AND RECOVERY-CYCLE SEMANTICS
4.1 Manager State Versus Cycle State
The recovery manager may be IDLE, AVAILABLE, UNAVAILABLE, or FAULTED.
An individual recovery cycle is separately represented.
Define:
[ RecState= {PENDING,ACTIVE,FAILED,SUCCEEDED,EXHAUSTED,CANCELLED} ]
IDLE is removed from individual recovery-cycle records.
4.2 Recovery-Cycle Identity
A cycle record contains:
[ Rec(q)= (instance,incidentId,state,attempts, maxAttempts,budgetRef,history) ]
Every newly created cycle receives a fresh identifier.
A terminal cycle is never reopened.

4.4 Attempt Accounting
An attempt allowance is consumed atomically at admission.
Let:
[ AttemptsRemaining(q)=maxAttempts(q)-attempts(q) ]
An admitted attempt that crashes remains counted.
4.5 Resource Reservation and Settlement
The canonical budget ledger (Q) records:
[ Budget=(allocated,available,reserved,consumed) ]
With:
[ \boxed{allocated=available+reserved+consumed} ]
A successful resource release transfers an amount from reserved to available.
A confirmed expenditure transfers an amount from reserved to consumed.
An unresolved crash reservation remains reserved until an authorized settlement decision; it is not silently refunded.
All accounting changes are atomic.
4.6 Retry Eligibility
A retry is eligible only if:
[ \begin{aligned} RetryEligible(q)\iff{}& state(q)=FAILED\ &\land AttemptsRemaining(q)>0\ &\land ResourceAvailable(q)\ &\land IncidentBudgetAvailable(q) \end{aligned} ]
If this predicate is false, a trusted exhaustion-evaluation event shall terminalize the cycle.
4.7 Administrative Reset
Administrative reset does not change:
[ EXHAUSTED\rightarrow PENDING ]
Instead, it may authorize creation of a new cycle:
[ q_{\mathrm{new}}\ne q_{\mathrm{old}} ]
The old cycle remains terminal.
Resetting an incident-level quota requires separate authority and is not implied by creating a new cycle.

5.1 Activation State
Define:
[ ActState= { AWAITING_ACK, ACKNOWLEDGED, COMPLETED, FAILED, EXHAUSTED, CANCELLED } ]
5.2 Activation Record
[ Act(a)= (instance,incidentId,cycleId, status,deadline,wakeCount, budgetRef,generation) ]
The generation field refers to the trusted request/session generation declared by the activation protocol, not an independently writable session epoch.
5.3 Open-Request Uniqueness
For any recovery cycle (q):
[ \left| {a:cycle(a)=q\land Open(a)} \right|\leq1 ]
Where:
[ Open(a)\iff status(a)\in {AWAITING_ACK,ACKNOWLEDGED} ]
An incident-level budget prevents repeated request creation from replenishing an exhausted allowance.

An ACKNOWLEDGED request is not subject to further heartbeat wake-ups.
Recovery execution after acknowledgement is governed by the recovery manager and its attempt timeout.
5.5 Deadline and Acknowledgement Ordering
For an acknowledgement:
[ AckValid(a,\tau) ]
requires a matching request generation, authenticated endpoint, and an open request.
An acknowledgement arriving after a nominal deadline may still be accepted if no competing terminal transition has committed and policy permits late acknowledgement.
The reference kernel SHALL use commit order to resolve the race.
At identical timestamps, the first valid committed transition wins; the later event revalidates against the resulting state.
No event may be authorized solely on a stale pre-commit snapshot.
5.6 Heartbeat Wake-Up
A heartbeat wake-up SHALL:
1. Validate the activation request.
2. Validate linked recovery eligibility.
3. Validate current lifecycle and session authority.
4. Reserve the wake-up budget.
5. Record the wake-up attempt.
6. Increment the wake-up count.
7. Establish the next deadline.
8. Emit the bounded activation command.
The activation remains AWAITING_ACK.
5.7 Wake-Up Exhaustion
After the last permitted wake-up, the request remains AWAITING_ACK until acknowledgement, terminal recovery outcome, cancellation, or final deadline expiry.
At the final deadline, an unacknowledged request transitions to EXHAUSTED.
5.8 Acknowledgement Is Not Success
The following are distinct:
1. Activation acknowledged.
2. Recovery attempt admitted.
3. Restoration validated.
The heartbeat's activation supervision ends after a valid acknowledgement.
A subsequent recovery crash requires independently governed recovery handling.

6. CROSS-MACHINE SYNCHRONIZATION
6.1 Recovery Eligibility
Define:
[ RecoveryActivationEligible(q) ]
To require:
• The cycle exists.
• It is not terminal.
• The instance is ACTIVE.
• No shutdown or suspension fence is pending.
• The incident has available activation authority.
• The current session authority is valid.
• No conflicting activation request is open.
For a wake-up on an existing request, the last condition is evaluated as uniqueness of that same request, not absence of all requests.
6.2 Recovery-to-Activation Terminal Cascade
When a recovery cycle commits:
• SUCCEEDED: Linked open activation becomes COMPLETED.
• EXHAUSTED: Linked open activation becomes FAILED, unless already terminal.
• CANCELLED: Linked open activation becomes CANCELLED.
These changes are atomic.
A recovery cycle reaching FAILED is not automatically terminal if retry remains available.
6.3 Activation-to-Recovery Outcome
Activation exhaustion does not automatically exhaust the recovery cycle.
The recovery manager shall evaluate:
• Whether an attempt is already ACTIVE.
• Whether a trusted recovery endpoint accepted activation.
• Whether additional activation is permitted.
• Whether incident policy requires closure.
An ACTIVE recovery attempt may continue after activation exhaustion if it retains valid execution authority.
No new activation budget is created automatically.
6.4 Shutdown-Intent Fence
The control plane SHALL support a governed shutdown or suspension intent.
Once that intent commits:
• New heartbeat wake-ups are prohibited.
• New recovery attempts are prohibited.
• New ordinary protected cognitive writes are prohibited.
• Delayed acknowledgements cannot reactivate the instance.
Already admitted operations must be settled, cancelled, or recorded unresolved.
6.5 Final Lifecycle Transition
Before committing SUSPENDED, STOPPED, or TERMINATED, the control plane SHALL:
1. Fence ordinary execution authority.
2. Halt or mark unavailable the heartbeat.
3. Terminalize open activation requests.
4. Terminalize or account for open recovery cycles.
5. Classify unresolved transactions and effects.
6. Meet the required preservation or stop contract.
The final lifecycle transition is atomic with the required authoritative state updates.
6.6 Failed Shutdown
If the trusted control plane cannot establish the required fencing or preservation conditions, it SHALL NOT claim that a safe suspension or stop completed.
The failure must be recorded with a defined unresolved-control outcome.
6.7 Transition Ordering
Build 2 is a sequential reference model.
Events are processed in a total committed order.
Priority may guide scheduling, but correctness SHALL depend on commit-time guards and atomic transitions, not solely on a static priority list.

7.3 Permitted Outputs
The heartbeat may produce only:
• Governed progress observations.
• Bounded activation wake-up requests.
• Governed fault or state-transition reports.
It cannot:
• Directly modify canonical fencing authority.
• Grant ADMIN CLASS permissions.
• Diagnose arbitrary cognitive faults.
• Declare its own health conclusively.
• Repair arbitrary NNNC components.
• Override authorized shutdown.
7.4 Progress Evidence
Progress evidence must be corroborated by the trusted transition kernel.

[ Progress= (sessionRef,observedGeneration, eventId,clockDomain,tick,stateVersion) ]
The observed generation is an evidence snapshot, not a second authoritative epoch.

[ Participation(H) ]
As the existence of governed effects attributable to the heartbeat in valid transition traces.
Define:
[ Advantage(H) ]
As improvement in predeclared external engineering outcomes relative to suitable alternatives.
Participation does not imply advantage.

8. FUNCTIONAL-MODE DERIVATION
8.1 Effective Health
Health evidence is evaluated against the current trusted clock domain and freshness requirements.
Expired or untrusted evidence evaluates to UNKNOWN.
8.2 Heartbeat DEGRADED Semantics
For Build 2:
• HEALTHY: Full heartbeat contract satisfied.
• DEGRADED: Minimum heartbeat progress contract satisfied, but nonessential capability reduced.
• FAILED: Minimum heartbeat progress contract violated.
• UNKNOWN: Insufficient current trusted evidence.
8.3 Total Mode Function
For non-ACTIVE lifecycle:
[ Mode=NONE ]
For ACTIVE lifecycle, evaluate in order:
1. If heartbeat is FAILED or UNKNOWN, or cognition is UNKNOWN: FAULTED.
2. Else if cognition is FAILED: MINIMAL.
3. Else if cognition, heartbeat, or recovery is DEGRADED, or recovery is FAILED or UNKNOWN: DEGRADED.
4. Else: FULL.
This function is total for the 64 possible three-component health vectors.
8.4 Conformance Profiles
FULL: Heartbeat, recovery, and cognitive placeholder satisfy full required contracts.
DEGRADED: The minimum heartbeat contract and a usable cognitive capability remain, but one or more nonessential or recovery capabilities are degraded or unavailable.
MINIMAL: Cognition is unavailable, but the minimum heartbeat contract remains satisfied.
FAULTED: Required existential evidence or a required minimum contract is unavailable or violated.
FAULTED does not automatically mean that every component has stopped executing.
8.5 Mode Evaluation
The derived mode is evaluated:
• At relevant committed health transitions.
• At trusted evidence-expiry events.
• At lifecycle transitions.
• During conformance queries against current trusted time.
Mode is not independently writable.

9. CHECKPOINTS, BRANCHING, AND UNRESOLVED EFFECTS
9.1 Classification Precedence
For checkpoint partitions:
[ INVALID>TAINTED>PARTIAL>CONSISTENT ]
The overall checkpoint classification uses the most severe applicable classification.
Per-partition classifications are retained.
9.2 Forced Suspension
Forced suspension may preserve healthy control-plane partitions while marking cognitive partitions TAINTED or PARTIAL.
It SHALL NOT claim a consistent checkpoint when required state is unverified.
9.3 Restoration Authority
Restoration cannot restore:
• Old fencing authority.
• Revoked permissions.
• Consumed budgets.
• Retired recovery cycles as active cycles.
• Prior event identifiers as unused.
• Stale clock-domain authority.
9.4 External Effects
Every unresolved external effect must carry a stable effect identifier.
On restoration, the system must distinguish:
• Completed.
• Pending.
• Cancelled.
• Compensated.
• Unknown.
An unknown effect SHALL NOT be blindly replayed as though it had never occurred.

10. DELEGATION AND TRUSTED SYSTEM EVENTS
10.1 Delegation Attenuation
For delegation chain scopes:
[ Scope_{i+1}\subseteq Scope_i ]
Each delegation must have:
• Authenticated issuer.
• Authenticated recipient.
• Operation and target scope.
• Expiry.
• Revocation reference.
• Maximum delegation depth.
• Non-cyclic chain structure.
10.2 Current-Policy Evaluation
Caller-provided policy versions are untrusted claims.
The kernel compares them against authoritative committed governance state.
10.3 System Principals
Trusted timer services, fault traps, and administrative controllers are explicit system principals.
They receive only the authority necessary for their declared event classes.
10.4 Fault-Report Limits
Fault reports require authenticated provenance, deduplication, and bounded incident-level resource consumption.
Unlimited creation of fresh recovery cycles for the same unresolved incident is prohibited.

11. STRENGTHENED INVARIANTS
The following invariants extend the v1.3 register.
S0-43 — Coupled Request Uniqueness
At most one open activation request exists per recovery cycle.
S0-44 — Recovery Terminal Synchronization
Terminal recovery outcomes atomically terminalize linked open activation requests.
S0-45 — No Automatic Exhaustion Equivalence
Activation exhaustion does not imply recovery-cycle exhaustion.
S0-46 — Shutdown Fencing
After shutdown intent commits, no new ordinary wake-up, recovery attempt, or cognitive protected write may be admitted under retiring authority.
S0-47 — Non-Rollback Authority
Checkpoint restoration SHALL NOT reduce fencing high-water marks, resurrect revocations, replenish consumed budgets, or invalidate committed replay-protection history.
S0-48 — Fresh Cycle Identity
A terminal recovery-cycle identifier SHALL NOT be reopened.
S0-49 — Clock-Domain Validity
Deadline comparisons SHALL use matching trusted clock domains.
S0-50 — Canonical Budget Conservation
Every committed budget operation SHALL preserve the ledger conservation invariant.
S0-51 — Branch Identity Uniqueness
Independent branches SHALL receive fresh instance and constituent identifiers.
S0-52 — Delegation Attenuation
No delegated protected operation may exceed the effective authority of its valid delegation chain.
S0-53 — Mode Totality
Every valid lifecycle and effective-health combination derives exactly one permitted functional mode.
S0-54 — Heartbeat Resumption Authorization
A HALTED heartbeat may resume only under governed lifecycle resumption and valid session authority.
S0-55 — No Self-Certified Heartbeat Health
Heartbeat self-reports alone SHALL NOT establish trusted operational conformance.
S0-56 — External-Effect Replay Safety
Unknown external effects SHALL NOT be automatically replayed as new effects.

12. BUILD 2 VERIFICATION OBLIGATIONS
12.1 Finite Reference Model
The initial independent model shall use bounded domains, for example:
• Two NNNC instances.
• Two recovery cycles per instance.
• Two activation requests per instance.
• Three recovery attempts per cycle.
• Three wake-up allowances per incident.
• Two administrative principals and two ordinary principals.
• Three clock domains.
• Finite lifecycle, heartbeat, recovery, and activation state enumerations.
• Abstract fresh session generations without wraparound.
These are proposed model bounds, not executed checks.
12.2 Safety Properties
The model shall check:
1. No stale protected write commits.
2. No duplicate current session authority.
3. No rollback resurrection of permissions.
4. No consumed-budget refund through restoration.
5. No duplicate open activation requests.
6. No automatic recovery retry after exhaustion.
7. No activation after shutdown fencing.
8. No illegal heartbeat resumption.
9. No inconsistent lifecycle-mode combination.
10. No independent branch sharing original constituent identifiers.
12.3 Liveness Properties
Under declared fairness assumptions, the model shall check bounded-response properties for:
• Timer delivery.
• Activation acknowledgement or exhaustion.
• Recovery attempt completion, timeout, or cancellation.
• Authorized shutdown completion or explicit failure.
• Incident terminalization.
Liveness is conditional on the relevant trusted services remaining available.
12.4 Independent Oracle
The executable Python kernel SHALL NOT be its own sole correctness oracle.
A separately specified transition model or independently implemented reference oracle must supply expected outcomes for differential testing.

13. EXPERIMENTAL ACCEPTANCE
13.1 Equal-Budget Comparison
Compare baseline and heartbeat architectures under the same total computational and resource budget.
13.2 Mechanism-Matched Comparison
Compare the heartbeat with an alternative conventional supervisor providing equivalent:
• Timer access.
• Fault reporting.
• Recovery activation.
• Session fencing.
• Transaction logging.
The alternative shall not be intentionally deprived of functionality merely to favor the heartbeat.
13.3 Primary Outcomes
Predeclare:
• Recovery completion probability within a fixed observation horizon.
• Time unavailable.
• Protected-state corruption rate.
• False activation rate.
• Total resource expenditure.
Unrecovered runs shall remain in the outcome dataset.
Time-to-recovery analysis should handle unrecovered observations as censored where statistically appropriate, while reporting failure rates separately.
13.4 Interpretation
Passing heartbeat-specific conformance tests establishes protocol participation.
Only comparative evidence can establish engineering advantage.
A simpler mechanism performing equally well or better remains a legitimate result.

A.4 Outstanding Semantic Review Points
Two transition relationships require particular attention in subsequent verification.
Suspension versus termination: Both may fence ordinary execution authority, but suspension permits governed resumption whereas termination does not imply resumption of the same operational instance. The transition model must preserve this distinction.
Activation exhaustion versus recovery eligibility: A terminal activation request must never reopen. Any subsequent activation requires a separately governed request and available incident-level allowance. Creation of a fresh request identifier must not circumvent exhausted budgets.
These are verification and implementation obligations, not authorization to bypass the normative state machines.
